# Phase 6 — Quality, security and readiness

Baseline: ad9a2412ca99256176c9b884036b3b547b1e90f4. Branch: migration/phase6-quality-security. Scope: local V1 only. The Phase 5 database volume, archive, Astro/Vercel reference and original worktrees were excluded from the experiments.

## Architecture

The active application is Vite's HTML/TypeScript MPA (home, Privacy and Terms) plus the Fastify API and a separate worker process in the same codebase. In development Vite proxies /api without changing Origin; the built app uses Fastify on the same origin. Fastify serves an explicit static route list and named Vite bundles. PostgreSQL is the system of record; the enquiry and outbox intent share a transaction. The worker claims jobs through PostgreSQL and sends through Nodemailer to a fixed synthetic Mailpit address. Compose publishes loopback ports. The build and runtime do not require Astro, Vercel, Redis, Resend or Turnstile. Those files and older tests remain for review in Phase 7. The HTML retains some old Astro-generated attribute names as CSS selectors; removing them is not part of QA.

Node 26.13.0, npm 11.20.0, Docker Desktop 4.98.0/Engine 29.9.2, Compose v5.6.1, PostgreSQL 18.6 and Mailpit 1.33.0 were used. No application dependency or lockfile changed. The migration tool's pinned overrides remain in place and both migrations executed on native PostgreSQL.

No known Critical or High security defect remains in the tested local configuration. The rate limiter is in-memory, resets on restart and shares a bucket for proxied loopback clients. An Origin check constrains ordinary browser requests; it does not authenticate a local/native client that can set its own headers. The API has no cookie-based authority to steal. Local clients with access to loopback, the Docker socket, application files or the operator account are trusted in this threat model. The request-body limit is not a complete defense against slow connections, flooding, database pressure or log growth. Public deployment needs connection and request limits at ingress, an explicit proxy trust model, distributed abuse controls as appropriate, monitoring and restricted service credentials. Mailpit's inbox is unauthenticated by design and must remain local.

## Verification and recovery

- Native PostgreSQL suites exercised distinct sessions, atomic rollback on outbox insertion failure, HMAC retry, concurrent submissions, skipped locked rows, expired-lease recovery and stale-token fencing. The browser timeout test commits through the real API and withholds the response; a retry uses the same UUID and a material edit uses another. A changed payload with the original UUID returns 409. Browser suites cover both offer categories, true receipt, worker stopped, real Mailpit connection failure/retry, database outage and safe error messaging. Controlled transport tests cover terminal exhaustion and permanent rejection. A separate real worker experiment killed only the synthetic worker during a stalled SMTP connection, waited for its actual 60 s lease to expire without changing database timestamps, and observed attempt two deliver one Mailpit capture. A closed loopback SMTP port also produced a recorded terminal failure after two attempts while the enquiry remained accepted. No external SMTP or real recipient was used.
- The extra HTTP experiment made 30 sequential requests (initial submission plus replays) and 12 concurrent requests sharing another UUID. PostgreSQL held only two enquiries and two jobs, both sent once to Mailpit. SQL-shaped text was stored literally and HTML-shaped text was escaped in the captured HTML. An unexpected JSON field was rejected. The real browser tests checked that contact data did not enter browser storage or the URL.
- A separate Compose project on loopback was used for verification. Restarting PostgreSQL, restarting Fastify, and recreating the two containers without removing the named volume preserved both rows, identities and delivery state. Replaying the same UUID did not create another job or notification. The regression suite also exercised the documented host-mode backup commands and refused to overwrite a restore target. A separate Compose pg_dump -Fc and transactional pg_restore produced a 10,617-byte mode-0600 synthetic archive; all rows in the migrations, enquiries and outbox tables matched a distinct restored database. The original Phase 5 volume and archive were not used.
- Static routes use explicit files and reject unsupported paths, env files, backups, source, manifests and unpublished assets. HTML and API responses use no-store; named fingerprinted JS is immutable. Input constraints include exact allowed origins, 32 KiB JSON, strict fields and offer IDs, a honeypot, and safe database failures. Logs intentionally omit request bodies and raw driver/SMTP messages. The pattern scan and built bundle check passed, but are not a full historical secret or infrastructure scan.

## Performance

Final dist payload was 256,162 bytes before compression (includes static metadata and header artifacts). JS: 13,074 raw / 4,853 gzip bytes, +179 raw bytes over the Phase 5 reference. Shared CSS: 25,606 / 5,827 bytes; homepage CSS: 11,444 / 2,665 bytes. The clock/logo PNG is 36,461 bytes. Homepage HTML is 99,868 raw / 15,492 gzip bytes. Gzip values are estimates from local compression, not a claim that the current Fastify server negotiates gzip.

Three cold Chromium trials per profile, HTTP loopback, external asset requests blocked, on this Mac. The trials preceded the last 219-byte CSS wrapping addition; the final responsive snapshots and interactions were rerun. Desktop (1440×900) LCP: 44–48 ms; load: 39–42 ms. Mobile (390×844, 4× CPU slowdown, 150 ms latency, 1.6 Mbit/s down / 0.75 Mbit/s up): LCP 940 ms in all three samples; load 1.12 s. No initial layout shift or >=50 ms task was observed in these samples. The two scripted FAQ clicks produced Event Timing maxima of 24 ms desktop and 32–40 ms mobile; this is not a field INP score. Fine-pointer chronograph movement ran at 16.7–16.8 ms p95 frame interval and stopped after leaving view. No Lighthouse, field Core Web Vitals or production-scale inference is made.

Local sequential HTTP latency (30 requests): median 1.39 ms, p95 3.20 ms. Concurrent same-UUID latency (12 requests): median 7.55 ms, p95 9.83 ms. PostgreSQL EXPLAIN used the enquiry primary key and the outbox pending partial index for the tested UUID lookup and due-work predicate; this does not characterize large-queue plans. The idle worker gained about 0.01 CPU seconds over 5.2 s and used ~89 MiB RSS. One Docker stats sample showed PostgreSQL ~59 MiB and Mailpit ~17 MiB. Figures describe the local fixtures and may vary with contention, fonts and hardware.

## Privacy and launch decisions

Contact data lives in the browser form and current-page retry memory, request and server process memory, PostgreSQL enquiry rows, the rendered worker message in memory, the Mailpit capture store, and backups or restored databases. Outbox rows retain the enquiry key and delivery metadata rather than a second full copy of the contact details. The HMAC key is separate server configuration, not part of a database dump. Mailpit captures may be cleared during recreation, but sent state remains in PostgreSQL. An ambiguous SMTP acknowledgement can result in duplicate notifications; durable acceptance and outbox uniqueness do not imply exactly-once email.

There is no approved retention/deletion schedule, final legal sign-off, confirmed public business identity, public hosting configuration, public anti-abuse policy or production SMTP provider. Owner review must align Privacy/Terms with the actual production data flow, including DB, backup, notification processor and optional Google Fonts. Choose credentials, encryption, monitoring and recovery policies before public operation. No policy or legal claim was changed here.
